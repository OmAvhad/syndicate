# Dashboard shielded deposits

Both roles use the dashboard's **Your shielded funds** panel. Link a MetaMask funding wallet, create a shielded wallet (or restore a backup), back it up, choose ETH/USDC/WETH and select **Load funds**. MetaMask switches to Ethereum Sepolia and requests the required approval and deposit transactions. Refresh private balances after confirmation; indexing may lag the receipt.

Each authenticated profile, linked funding address and chain has its own persistent wallet namespace. Wallet creation saves a cryptographically generated mnemonic before preparing any deposit. Kohaku derives the spending and viewing keys using its own key paths and creates randomized encrypted note commitments through prepareShield. There is no custom application nullifier or salt hash scheme.

Balance loading uses one SDK note synchronization for both totals and note counts. Concurrent refreshes in the same browser tab share a single request; operations across tabs queue on the wallet lock. The last synchronized balance is stored locally with its timestamp for immediate display, and navigation within 30 seconds reuses it. Manual refresh forces a new sync. Deposits and withdrawal submission invalidate the display cache; trade funding independently synchronizes spendable notes. First-time synchronization still depends on the indexer/RPC and can take longer.

The seed and derivation index stay in localStorage. The complete SDK database stays in a namespaced IndexedDB database, including the SDK's private note data and synchronization state. The spending/viewing keys and recovered notes are the inputs Kohaku will use to construct nullifiers/proofs later. A reload reuses the same keys; it never rotates them automatically. The dashboard does not implement spending yet.

## Leader trade funding

Before submitting, select **Prepare proof files** on `/trade`. The app verifies and caches 75 public proving files (25 supported non-POI circuits, about 179 MiB) from its own static assets and shows progress/Ready. Subsequent visits reuse the versioned browser Cache Storage. Missing files block proof generation rather than downloading during submission; existing submitted operations can still be reconciled without preparing again.

Run `npm run artifacts:prepare` in `frontend` to populate its ignored `public/proving-artifacts/` directory. The script pins repository revision `5dd976e5dbf059daa227819df0d3054c83ccccd9` and checks each file's size and Git blob hash. `npm run build` runs this automatically, reuses verified files, and includes them in the static build. Files use a neutral `.artifact` extension so hosts do not automatically decompress their internal Brotli payloads; the SDK handles that decompression. Deploy all of `dist`, including proving-artifacts. Cache entries are verified on preparation and partitioned by pinned revision; clearing site data requires preparation again.

The `/trade` page now reads that same shielded wallet and displays private USDC/WETH balances. Submitting checks USDC capital plus the pool's configured withdrawal fee, a native ETH entry/exit reserve and a conservative WETH withdrawal-fee budget. Insufficient balances link back to the dashboard for top-ups. Estimates depend on current gas price and are not fixed final fees.

Submission generates a real burner on the device and saves its private key and funding state in localStorage. Using only public SDK APIs, the funding adapter derives the original shielded spending/viewing keys, synchronizes its notes, builds USDC and WETH unshields to the new burner, and includes WETH unwrapping to provide native execution gas. The same recipient burner signs the EIP-7702 UserOperation locally. Pimlico estimation is checked against the reserved withdrawal budget before submission.

The backend requires PIMLICO_API_KEY (existing root/backend environment loading). An authenticated short-lived bundler session permits only supported methods and operations for its declared burner. The browser receives no Pimlico API key, shielded keys or server signing key. Only the signed UserOperation is relayed. Restart the backend after adding configuration; the browser uses the configured VITE_API_URL.

The actual UserOperation hash and funding transaction are saved. The flow checks operation success and burner USDC/native balances before creating the promise. Entry and exit explicitly use the saved burner key. Retries reuse the same burner and, after an uncertain broadcast, the same signed operation. Entry-pending state blocks automatic duplicate trading; an interrupted entry needs receipt/balance inspection. Local keys remain saved for recovery and exits. Closed burner records are retained.

After Pimlico estimation, the preliminary withdrawal budget is replaced by the live operation's maximum gas cost, with an allowance for the pinned SDK's 1% fee-note convergence tolerance. The app compares total required WETH (that allowance plus gross native-gas withdrawal) against the synchronized shielded balance; exceeding the earlier rough quote alone is not an error. Logs show the live estimate and available balance, and any real shortfall reports exact required/available/top-up values. This allowance is a balance check, not an additional fee transfer.

The existing demo executes separate ERC-20 transfers through its configured vault; this integration does not establish an atomic swap or a Definitive fill. Its trading WETH remains distinct from pool WETH. The USDC principal and native gas handoff do not mix these ERC-20 balances. Follower execution still uses the earlier static follower account.

Follower signal recovery: cancel a stuck MetaMask request, then select **Refresh encryption key & retry** in the copy modal. This asks MetaMask for the current account's encryption public key, re-encrypts only the authenticated follower's still-active signal delivery, and opens a fresh eth_decrypt request. The server returns no plaintext, does not extend expiry, and retains the original Arkiv ciphertext. Invalid envelopes and wallet mismatches are checked before opening decryption. Changing a linked wallet clears its previous encryption key until the new wallet authorizes one. This recovery handles stale encryption material; it does not establish the cause of a wallet UI refusing to decrypt a fresh, valid request.

Tests now cover fee rounding, insufficient USDC/WETH, recipient/signer equality, saved funding evidence, uncertain submission retries and failed funding, plus browser gating on the leader page. The live browser's seeded wallet/funds are needed for a real funded withdrawal; no live user funds were spent during implementation. The existing shielded backup covers its seed/note database; per-trade burner records must also be preserved in browser storage for open positions.

**Back up shielded wallet** exports a private JSON file containing recovery material and the SDK database. Restore requires the same linked funding address and Sepolia, and refuses to overwrite an existing local wallet. Refresh after restore to synchronize with the chain. Keep this unencrypted file private. These PoC browser stores are also unencrypted, and clearing them without a backup loses local access.

Transaction history distinguishes submitted, confirmed, reverted and interrupted deposits. Pending hashes survive reloads and are reconciled during balance refresh before another deposit is allowed. ETH shielding credits the pool's WETH token, not the different WETH contract used by the existing trade demo. POI remains disabled, matching the standalone testnet demo.

Optional frontend configuration: VITE_SEPOLIA_RPC_URL overrides the public Sepolia RPC. No server signing keys or Pimlico credential is needed for deposits. Existing funds in the standalone portal's server wallet are not migrated into newly created browser wallets.

Sepolia traffic from the pool and transfer engine shares one serialized request queue (at least 400 ms between requests). Concurrent identical reads are combined; chain ID, latest block and gas price have short caches. HTTP 429/rate-limit errors retry with 2/4/8/16-second backoff and show a status in the terminal, then stop with an actionable error. Contract balance reads are not cached beyond in-flight deduplication. To increase provider capacity, set VITE_SEPOLIA_RPC_URL in frontend/.env.local and restart Vite; root SEPOLIA_RPC_URL does not configure the browser bundle. The currently configured root endpoint is also PublicNode.

Validation: npm test checks recovery, isolation, backup state, amount precision, pending receipts, reverts and changed funding accounts. After npm run build, npm run test:browser checks real browser/WASM initialization, address persistence and mobile layout using mocked backend/chain responses. Set POOL_TEST_DEV=1 to exercise the development server. Browser tests use installed Microsoft Edge. These checks do not demonstrate a live funded Sepolia deposit or later withdrawal.
